# Feed scope and sources

## Scope
- 2026-11-26: Niko: "I don't want this to be a threat feed." The main feed shows only things a person could be affected by: breaches, confirmed ransomware attacks, leaks, and exploited or critical flaws in widely used products.
- 2026-11-26: "All events" requires a named affected organization or product. Threat research, malware analysis and espionage reports go under Research. Attacker claims with no other coverage stay under Ransomware, labelled as claims, and out of the main feed.
- 2026-11-26: A CVE appears only when it affects a product on a curated list of things people use (Windows, iPhone, Android, Chrome, routers, popular apps) and is rated critical or is being exploited. CVE rows carry the product's logo and a plain-language line.
- 2026-11-26: GitHub Security Advisories were dropped from the MVP (library flaws mean nothing to the audience).
- 2026-11-26: Niko raised fetching ransomware gangs' .onion sites or X accounts directly. Decided against: attacker claims come only through Ransomware.live, and the site never fetches or links to leak sites. Reasons: Ransomware.live already monitors them; it would mean running Tor against criminal infrastructure, which the brief forbids; the pages host stolen personal data; X's API is paid.
- 2026-11-26: Entity extraction is deterministic: structured fields where a source provides them, plus a curated alias dictionary of vendors and products matched against headlines; otherwise "unknown". The LLM also proposes an organization (see [LLM usage](llm-usage.md)).
- 2026-11-26: Stored per source record: headline, link, timestamps, extracted metadata, and a plain-text excerpt capped near 300 characters. Full feed text is discarded at ingestion.
- 2026-11-26: First run backfills 30 days from structured sources plus whatever each news feed holds; everything is kept from then on.

## Fetching as built, 2026-11-26
As of `NikoTsiolas/Compromised.io@0066781` (ticket #3, built by an Opus subagent, CI green on that commit):
- All 10 RSS news and research sources had registry entries with tier, weight, interval and size cap; weight defaulted to the tier's base score (official 90, press 50, claim 20). Krebs carried a 35-second crawl delay.
- Only registry hosts over HTTPS were fetched. Redirects were followed by hand, at most three, each target re-checked; off-list, downgraded or over-limit redirects were refused.
- Connect, read and whole-attempt timeouts; a size cap on the decompressed body; retries on 429, 5xx and timeouts with doubling backoff never shorter than the crawl delay. Tested against a local HTTPS stub server in a CI step named "Fetcher seam".
- ETag and Last-Modified were stored and sent; a 304 skipped parsing. Any DOCTYPE before the root element was refused, in addition to feedparser not resolving external entities.
- `GET /v1/status` returned overall status (starting, live, degraded, down) and each source's state and last success, without error text.
- The worker derived what was due from `last_attempt_at` in the database, so a restart did not re-poll every source.
- Source ids `cisco-talos` and `google-threat-intelligence` matched the fixture names. The migration was `003_source_registry_and_health.sql`. Browser-suite ports could be overridden with `E2E_API_PORT` and `E2E_WEB_PORT`.
- A real check on this date fetched each of the 10 sources once; all succeeded (200 items). SecurityWeek's second fetch returned 304.

Friction the subagent reported: `mvp` moved twice under it and the ticket #6 merge conflicted in 8 files; the auto-mode classifier blocked running the long-lived worker loop, so real feeds were checked with one-off passes.

## MSRC re-ratings as revisions, 2026-11-26
As of `NikoTsiolas/Compromised.io@4863218` on branch `merge-tickets-4-5-8` (merge of #4, #5 and #8, by an Opus subagent):
- Contradiction found at the merge: #4 overwrote a stored MSRC record's metadata when a later revision changed Microsoft's rating, while #5's trigger (`004_grouping.sql`) refused any change to a source record other than `event_id`. Merged as built, a re-rating failed the whole MSRC poll.
- Decision (coordinating session, 2026-11-26): source records stay exactly as fetched. A re-rating is new information from a later fetch, not a correction of the earlier one, so it is appended, never written over; the spec keeps original records so that grouping mistakes and later corrections never lose data.
- As built: migration `006_record_revisions.sql` added `source_record_revisions` (record id, fetch time, the source's `revised_at`, the changed fields), append-only by trigger. `storage.append_record_revision` replaced `update_record_metadata`. A record's effective metadata, its own overlaid with its revisions in order, is computed in one place (`storage.EFFECTIVE_METADATA`) and is what `event_records` and `record_by_id` return, so the classifier, scope rules and vulnerability gate (and #7 later) read the latest rating. The API exposes nothing new.

## CISA advisories and MSRC fetch failures diagnosed, 2026-11-26
A subagent investigated at `origin/mvp` as of this date, with 6 real requests to www.cisa.gov and 5 to api.msrc.microsoft.com. No code was changed.
- MSRC: the feed itself answered 200. The 400 came from the SUG lookup. On a fresh database 1,007 CVEs of listed products fell inside the 30-day window, and `msrc.BATCH = 40` built a `$filter` of 40 `cveNumber eq` terms; the API replied "Failed validating query options" at 40, 26 and 25 terms, while a 3-term query had worked earlier. The limit lies somewhere between 4 and 24 terms; not pinned down. The cause is in our code, and the volume (about a thousand CVEs on first run) is itself a design problem.
- CISA advisories: the fetcher's request got 403 three times from Akamai (a 410-byte page with an `x-reference-error` header). curl with the same user agent got 200 over HTTP/2, over HTTP/1.1, and with httpx's exact headers; a Python request copying curl's header order still got 403. The remaining difference was the TLS handshake (Python's OpenSSL 3.0.14 against curl's LibreSSL), which Akamai appeared to fingerprint on this path but not on the KEV file. Decision by Claude: no workaround. Changing the TLS stack to get past a bot filter would be evading the block. The source stays in the registry to see whether Railway's environment is accepted; if it is refused there too, it is dropped. CISA KEV is unaffected.
- This supersedes the earlier belief on this date that dropping "Bot" from the user agent had fixed CISA advisories: the 200 recorded then came from a curl request, not from the fetcher.

## Widget figures as built, 2026-11-26
On branch `ticket-15-widget-data` (ticket #15, built by an Opus session; not merged on this date):
- The whole CISA KEV catalog is kept in its own table, `kev_catalog_entries` (migration `010_kev_catalog.sql`; CVE, vendor, product, name, date added, known ransomware use), replaced in one transaction every time the worker gets a full catalog (a 304 leaves it). A one-row `kev_catalog` table records the catalog's version, the size it declares and the entries kept. No feed event is created for entries older than the 30-day backfill. Monthly counts are a grouping over the stored entries, by calendar month in UTC, so they cannot drift from the catalog. Decision by Claude: store entries, not month totals, because notable entries and "recently exploited" need them.
- Spike rule (decision by Claude, carried over from the chart component of #9 and moved to the API so the chart and the API agree): a month is a spike when its count is at least one population standard deviation above the average of the months shown (default 12, ending with the current month, which is partial), with at least three months and not all equal. The API sends `spike` per month and the rule's wording (`spike_rule`); the chart no longer computes it.
- Notable entries of a spike month (shown in the chart's tooltip as "<product>: <weakness>", the weakness being CISA's name without the vendor and product it starts with; the full name is also sent): entries whose product is on the "people use" list (matched as the feed's extractor matches KEV products) or that CISA marks as known ransomware use, newest first, at most three.
- Real check: one fetch of the catalog (version 2026.11.25) gave 1,805 entries, equal to its declared count. Last 12 months: Dec 20, Jan 17, Feb 28, Mar 26, Apr 31, May 21, Jun 23, Jul 26, Aug 31, Sep 43, Oct 36, Nov 39 (to the 25th). Average 28.4, deviation 7.6, threshold 36.0: September and November 2026 are spikes; October (36) falls just short.
- Recently exploited: the newest catalog entries in a product on the "people use" list, shown by day only (CISA records no time). Real check: Chrome (10 Nov), WordPress (3 Nov), Windows (13 Oct), Chrome (9 Sep), Windows (8 Sep).
- Most reported organisations: distinct events on the All tab published in the last 30 days, grouped by catalog key (else the name). The All tab already excludes commentary, research, flaws outside the "people use" list and attacker claims nobody else reported, so a claim never counts as a report; a claim that a news outlet or official source also covered counts once. Decision by Claude. Real check showed "Switzerland" counted as an organisation, an extractor result from #6, not changed here.
- Endpoints: `GET /v1/widgets/exploited-by-month?months=1..60` and `/v1/widgets/recently-exploited` (`Cache-Control: public, max-age=300`), `/v1/widgets/most-reported` (`max-age=60`). The homepage fills the three widgets from them and keeps each widget's empty state when a figure is empty or cannot be loaded.
- Not built: the sector and service-outage chart views (waiting for Niko's confirmation) and Trending (#10).
- Found with the real data: the chart's tooltip was cut off by its card (the shadcn Card clips overflow) once it held real CISA names; the sample data had been short enough to hide it. Fixed without changing the look: the widget card lets the tooltip overflow and is lifted above the widgets after it while the tooltip shows. A browser test checks the last notable entry is on top.

## Search, filters and Trending as built, 2026-11-26
On branch `ticket-10-search-trending` (ticket #10, built by an Opus session, not merged on this date):
- Migration `010_search.sql` gave events `cves`, `threat_actors`, `attack_vector` and a `search_vector` (tsvector, GIN-indexed). `scope.refresh_event` derives them from the event's source records on every refresh (records stay immutable). The migration backfilled CVEs and a basic vector in SQL; `pnpm db:reclassify` fills the rest on an existing database.
- Extraction was deterministic, in `pipeline/search_terms.py`; the model was never asked. CVEs: the union of the records' (found at normalization since #5). Threat actors: Ransomware.live's `group` field, catalog threat-actor names as whole words, and a name a source introduces ("a threat group called \"Volant Manticore\""). Attack vector: the first of 18 phrase rules that matches any headline or excerpt, most specific weakness first (SQL injection, command injection, ... phishing, social engineering, ... zero-day, exploited flaw).
- On the 35 events from all 39 real captured records: 17 got an attack vector and none of the 17 looked wrong on a read-through; "improper authentication" (Danfoss) was labelled authentication bypass, a stretch. Misses: "ARMORY CASTLE Exploits vSphere" and Krebs's Optimizely story (the flaw and "exploits" were more than 60 characters apart). Six events got a threat actor (Qilin, Salt Typhoon, Volant Manticore, Metaencryptor, Orova twice); Mandiant's cluster names (ARMORY CASTLE, COLD RELIC) were not recognised.
- `GET /v1/search`: `q`, `category`, `source`, `status` (each repeatable: OR within a field, AND across fields), `from`/`to` (UTC dates, both inclusive), `tab`, `limit`, `cursor` (the feed's cursor). CVE identifiers in `q` matched `events.cves` exactly; the rest went through `websearch_to_tsquery('english', ...)`, which never raises on operator characters. The search document weighted title, organization, the catalog vendor of the product ("Google" finds a Chrome flaw), threat actors, attack vector and structured product/vendor fields first, then every source's headline, then excerpts and the AI summary. Control characters (NUL among them) were stripped; a query of only punctuation matched nothing; values outside a filter's list, a query over 200 characters or a bad date were refused with 422, a tampered cursor with 400. Results were newest first, not ranked by relevance, so the existing cursor applied. `GET /v1/filters` listed each filter's values with labels; `EventOut` gained `cves`, `threat_actors`, `attack_vector`.
- Decision by Claude, Niko had not chosen on this date: search covered only events shown in at least one tab, so it kept the feed's quality bar (no commentary, unknown organizations or gated enterprise flaws). The alternative, every stored event, serves technical readers looking up a hidden CVE; it is one condition in `storage/search.py`.
- Trending (`GET /v1/trending`, and the Trending tab of `/v1/events`): every distinct news or official source that reported the event in the last 72 hours added 0.5 ^ (hours since that source's latest report on the event / 24). Attacker-claim sources added nothing and claim-only events never trended; only events in a tab were ranked; ties went to the newer event id. No engagement data exists or was used. Window and half-life were `storage/search.py` constants, sent in `GET /v1/scoring` and stated on the "How we score" page.
- Which time decays (decision by Claude): not the event's `published_at`, which is its earliest source's time (#5), because then an older story that fresh outlets pick up today would rank as old; and not the event's latest record alone, because one late mention would make every earlier source count as fresh. Each source decays from its own latest report, so each outlet's coverage counts for as recent as it is.
- Trending's cursor carried the time the first page was ranked at, so later pages continued the same ranking instead of one that had decayed in between.
- Web: `/search` (the header's search control and phone link land there) with the query and filters on shadcn Input, NativeSelect and Label; choosing a filter applies it at once; empty fields are left out of the URL. Results and the homepage feed both list events through `components/feed/feed-list.tsx`, so the social-feed redesign (#16) should change that component (or replace it in both places) rather than the search page. Technical details show the threat actors and "Not identified" for an attack vector looked for and not found.
